## 今週決めること

最初の問いは、**lag 11・SS=2 donor の真の最古 S が、lag 3/7/11 の窓からなる緊密回避集合に被覆されないことを、周期の上限なしに証明できるか**。
[仮説カード](HYPOTHESIS_CARD_2026-09-17_SHORT_TIGHT_DONOR_AVOIDANCE.md)に量化子を固定した。状態は `CONJECTURED`。

合格は、意図した量化を保つ非自明な補題の証明、正確な反例、または不足する局所入力を一つまで絞った停止判断。
Lean ファイル数・定理数・探索範囲の増加は合格基準にしない。全射性は今週の作業単位にしない。

前半の問いが判定できたら、後半は「長い窓に同じ供出回避を適用する際、任意 offset の所有者配置を排除する局所制約が得られるか」に最大2晩を使う。
この探索は新しいカードに命題を固定してから始める。一般 G1、E-070、E-067 の証明を週間の約束にしない。

第1週の成功は「限定された新補題を一つ得る」または「失敗する仮説を反例付きで一つ排除する」。
未着手や時間不足は証明失敗・反証と区別し、未完了の理由をそのまま残す。

9/21の必須反証項目: 根窓の S が offset k、所有者の所有 offset が kx、最古 S の offset が r、
所有者窓長が Lx のとき、`δ = r - kx ≥ 0` を保持する。
所有者の最古 S より古い A-tail が根の座標で占める範囲は `k+δ+1 .. k+(Lx-kx)`。
旧 OS 用の `k+1 ..` は `kx=r` の場合だけで、M1/M2 の任意所有 offset へ流用できない。
根窓と重なる範囲に制限して比較する。この座標変換自体は新しい研究成果ではなく、
実際の最小 P2 窓の条件から δ や配置に非自明な制約が得られるかを判定する。

## 毎晩の実行方法

予約は同じタスクを 01:00 / 01:30 / 02:00 / 02:30 に再開する。
親担当は日付・時刻・前回の引き継ぎを読み、Sol にその枠の限定した作業を渡し、結果と根拠を照合する。
数学の探索、反証プログラム、Lean の変更は Sol が行う。

- `collaboration.spawn_agent` を使う場合は `model="gpt-5.6-sol"`、`reasoning_effort="xhigh"`、`fork_turns="none"` を明示し、repo とカードの絶対パス、問い、前提、停止時刻、担当ファイルを渡す。
- 書き込み担当は一人。同じ枠で複数の実装者を走らせない。既存 worker が動いていたら重複起動せず状況を確認する。
- 提案・反証・形式化は別段階にする。全ての成果候補は、実装者とは別の新しい Sol に敵対的検証を委任する。実装者の自己点検で代用せず、下記の必須条件を満たすまで登録・昇格しない。
- Sol が利用できない場合は理由を知らせてその枠を止める。別モデルへ黙って代替しない。親が代わりに研究を始めない。
- 各枠の25分までに worker の記録を終え、親が引き継ぎを確認する。最後の枠は02:50までに worker を終了させ、03:00までにまとめる。実時刻を確認し、締切後に探索を継続しない。
- 長い処理は残り時間に応じて上限を付ける。時間切れの検証は未検証と記録し、`PROVED-LEAN` にしない。進展が無ければ時間を埋めない。
- 敵対的検証の時間を各枠に確保する。02:30の枠は未監査の候補の検証を優先する。時間不足や監査担当の起動失敗は免除理由にならず、次回へ未検証として引き継ぐ。

各晩の最初に当日の変更と他セッションの実行状態を確認する。本書作成後に証拠が変わっていたら、重複作業を避け、変更理由をカードに記す。
以後の記録は `docs/RESEARCH_HANDOFF_YYYY-MM-DD_SOL.md` と当該カードへ保存し、次枠が実行コマンドと未解決点を復元できるようにする。

## 必須の敵対的検証

**Lean が通ることと、研究として意味があることを別々に判定する。全ての成果候補に例外なく適用する。**
対象は Lean 定理だけでなく、紙上証明、計算による排除、反例、停止判断を含む。
草稿や原ログは保存してよいが、以下が未完了なら成果台帳への新規登録・証拠水準の昇格・後続証明の確立済み根拠としての採用をしない。
この手続きは研究ラベルを追加するものではなく、既存の証拠ラベルを付ける前の監査である。

1. **形式化前の入口検査。** カードに正確な量化子、仮定、結論、非形式的な依存鎖、既存成果との差分を記す。
   小例・境界例・弱化モデル・既知反例を試した記録を用意し、独立の反証担当が確認する。
   前提が実際に成立する具体例を調べる。対象が0件、仮定が矛盾、結論を仮定しただけなら、その原因を解決するまで新しい研究用 Lean モジュールを書かない。
   不可能性そのものを証明する場合は、何の実現可能な配置を排除するのかと、その研究上の用途を別途明示する。
2. **独立の検証担当。** 実装・提案した担当とは別に `gpt-5.6-sol` / `xhigh` / `fork_turns="none"` で起動する。
   カード、対象ファイル、既知反例、既存成果、検証期限を渡し、「正しさの追認」ではなく「主張を壊す」ことを依頼する。
   実装者の要約だけを根拠にせず、元の定義・signature・証明・実験コード・原ログを読む。
   研究ファイルは読取専用とし、必要な反例実験は隔離した一時領域で行う。修正とその合否判定を同じ担当に任せない。
3. **空虚性への攻撃。** 定義された `Prop`、構造体のフィールド、補助命題を展開して、結論の隠れた仮定化、循環依存、`H → H`、`x = x`、既存定理の包み直しを探す。
   軌道・符号語・窓への言及が飾りで、実体が自由変数上の算術だけになっていないか確認する。
   仮定を外す・結論を変える負の対照も試し、元の問題と無関係に証明が通っていないかを調べる。仮定が一つ不要というだけで誤りとはしない。
   算術の補助補題は許すが、それだけを研究の前進として登録しない。
4. **意味と反例への攻撃。** 日本語の主張と Lean の量化子・定義を両方向に照合し、空集合、周期境界、位相の同一視、最小性、履歴条件を検査する。
   実現可能な非自明例を確認し、既知の反例を誤って排除していないか試す。弱化モデルの反例と元の全仮定を満たす反例を区別する。
   未証明の定義済み仮定を使う条件付き定理は条件付きと明記し、その仮定を解消した成果として扱わない。
   有限計算から無限範囲、周期符号語から実軌道、G2から一般 Gate T6への飛躍を拒否する。
5. **証拠の再検証。** 反例は元の全仮定と結論の否定を検証担当が独立に再計算する。
   計算結果は対象数が非ゼロか、列挙と打切りの区別、seed、revision、未コミットソースのハッシュ、正確な出力を確認する。
   凍結 holdout と既知データを区別する。高価な検査が期限内に再現できなければ未完了とし、ログを読んだだけで独立再現済みとしない。
   Lean では `python3 scripts/report_vacuity.py --all <file>` の報告を読み、`harness_gate.py --lint-module`、statement audit、`./scripts/check.sh` の結果と照合する。
   自動検査はヒューリスティックを含み、通過しても意味の監査を省略できない。
6. **記録と判定。** 親担当が `docs/adversarial_audits/` にカードID・日時付きの監査記録を保存する。
   対象の revision と変更ファイルのハッシュ、担当、逐語 signature または正確な計算命題、試した攻撃、実行コマンド・出力、反例、依存義務、残る不確実性を記す。
   手続き上の判定は「合格 / 差戻し / 未完了」とし、証拠ラベルとは区別する。無条件の合格文だけの報告は受け付けない。
   差戻しは修正後の対象を再監査する。対象や依存先が変わった場合も旧版の合格を流用しない。
   検証担当の合格記録と必要な検査出力を親が照合して初めて登録できる。異論や未検証箇所が残れば主張を弱めて隠さず、そのまま保留・停止する。

監査の都合で命題を弱める、実体のない定理を増やす、ゲートを緩める、保護された主張を変更することは禁止する。
独立した担当も同じモデルの誤りを共有し得るため、独立性の宣言ではなく、具体的な攻撃・再現・依存関係の記録を証拠とする。

## 反証・計算プロトコル

既存の E-345/349/354/356 の計算範囲は既知データとして扱う。反例なしの再集計を新規 holdout にしない。

対象が0件なら「違反0」を成功にしない。探索打切り・cap は不明であり排除ではない。

## 登録・検証・報告

Lean 変更時は `./scripts/check.sh`、新 Lean モジュールには `python3 scripts/harness_gate.py --lint-module <file>`。
主要定理を `Recaman/Audit.lean` に入れ、新しい `PROVED-LEAN` 行は `--audit-template E-NNN` で作る statement audit に逐語 signature と意味監査を記す。
実際の書式は既存スクリプトの引数を確認する。検査ゲートを変更した場合だけ `bash scripts/test_harness_gates.sh` も実行する。

カードが stable になり、対象版への必須の敵対的検証が合格してから frontier / registry / proof map / development log を必要な範囲で同期する。
計画しただけの命題を新成果として登録しない。中心命題のラベルと `PROTECTED_CLAIMS.tsv` は変更しない。
`sorry` / `admit` / `native_decide` / 独自 axiom、未証明 Prop からの解決宣言、gate の迂回は禁止。
コミットする場合は自分の変更だけを明示したパスで行い、1新モジュール/commit と30分の間隔を守る。コミット数を目標にしない。

引き継ぎには、結論、カードの状態、変更ファイル、コマンド、最も強い証拠、失敗・反例、残る不確実性、次の判断を含める。
敵対的検証の記録パス、対象版、判定、未解決の指摘を必ず含め、未監査の候補を成果と混ぜない。
週間報告では「一般 p」と「一般 lag」と「実軌道」の到達範囲を分け、未解決部分を明記する。
